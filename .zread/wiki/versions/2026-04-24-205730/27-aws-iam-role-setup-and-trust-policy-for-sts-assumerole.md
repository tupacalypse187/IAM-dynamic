IAM-Dynamic operates on a **delegated authority** model: a long-lived IAM Role acts as the credential issuance authority, and short-lived session-scoped credentials are minted via AWS STS `AssumeRole` with inline session policies generated by the LLM. This page explains the IAM primitives involved, how the automated `setup-aws.sh` bootstrap script provisions them, and how the backend's `STSService` consumes them at runtime — covering the trust policy structure, permission scoping strategy, risk-based duration enforcement, and the end-to-end credential issuance flow.

Sources: [sts_service.py](backend/services/sts_service.py#L1-L155), [setup-aws.sh](setup-aws.sh#L1-L640), [config.py](backend/config.py#L27-L35)

## Architecture: The Credential Issuance Chain

Before diving into implementation details, it is worth understanding the three-entity trust chain that underpins every credential issuance. The **IAM User** (the application's persistent identity) assumes an **IAM Role** (the session authority) which, combined with a **Session Policy** (the LLM-generated least-privilege scope), produces temporary credentials with exactly the permissions requested — nothing more, nothing less. The role's trust policy is the gatekeeper: it determines *who* can assume the role, while the session policy determines *what* the resulting session can do.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    IAM-Dynamic Credential Issuance Chain                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌──────────────┐    AssumeRole     ┌─────────────────────┐                 │
│  │   IAM User   │ ──────────────▶  │   IAM Role           │                │
│  │(iam-dynamic  │   (trust policy   │(AgentPOCSessionRole) │                │
│  │   -app)      │    authorizes)    │                      │                │
│  └──────────────┘                   │ Base Policy: broad   │                │
│         │                           │ Session Policy: exact │                │
│         │  boto3 STS client         │ ┌──────────────────┐ │                │
│         │  (aws access keys)        │ │  LLM-generated   │ │                │
│         ▼                           │ │  inline policy   │ │                │
│  ┌──────────────┐                   │ │  (scoped per     │ │                │
│  │  STSService  │ ──Policy param──▶ │ │   request)       │ │                │
│  │  (backend)   │                   │ └──────────────────┘ │                │
│  └──────┬───────┘                   └──────────┬───────────┘                │
│         │                                      │                            │
│         │         Temporary Credentials         │                            │
│         │  ┌────────────────────────────────┐   │                            │
│         └──│ AccessKeyId + SecretAccessKey  │◀──┘                            │
│            │ SessionToken + Expiration      │                                │
│            │ (15 min → 12 hr, risk-scaled)  │                                │
│            └────────────────────────────────┘                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

The diagram above reveals a critical design principle: **the role's base permissions policy defines the ceiling of what is possible, while the session policy acts as the actual enforcement boundary**. The `IAMDynamicBasePermissions` inline policy grants broad access to common services (S3, EC2, Lambda, DynamoDB, RDS, CloudWatch, Secrets Manager) but the effective permissions of any issued session are the *intersection* of the role's policy and the session policy — meaning the LLM-generated policy can only restrict, never expand.

## IAM Role and Trust Policy Structure

### The Trust Policy

The trust policy (technically the role's *assume-role policy document*) is the JSON resource-based policy that governs which AWS principals are allowed to call `sts:AssumeRole` on this role. The `setup-aws.sh` script constructs a two-statement trust policy:

| Statement | Principal | Purpose |
|-----------|-----------|---------|
| **Service principal** | `sts.amazonaws.com` | Allows the STS service itself to process AssumeRole calls |
| **AWS principals** | Array of IAM user/role ARNs | Authorizes specific identities (the calling user + the `iam-dynamic-app` service user) |

The resulting trust policy document follows this structure:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "sts.amazonaws.com" },
      "Action": "sts:AssumeRole"
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": ["arn:aws:iam::123456789012:user/alice", "arn:aws:iam::123456789012:user/iam-dynamic-app"]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

The script dynamically detects the caller's identity type (IAM user, IAM role, or assumed-role) and constructs the appropriate principal ARNs. When the caller is an IAM user `alice`, the script adds `arn:aws:iam::<account>:user/alice`. When running inside an assumed role session (common in CI/CD or EC2), it extracts the base role name and constructs the role ARN. The `iam-dynamic-app` user's ARN is added if user creation is not skipped.

Sources: [setup-aws.sh](setup-aws.sh#L260-L277), [setup-aws.sh](setup-aws.sh#L180-L218), [AWS-SETUP.md](docs/AWS-SETUP.md#L195-L218)

### Principal Detection Logic

The `get_caller_identity_type()` function classifies the authenticated identity by inspecting the ARN pattern. This classification drives the trust policy construction:

| ARN Pattern | Detected Type | Trust Principal |
|-------------|--------------|-----------------|
| `arn:aws:iam::<account>:user/<name>` | `user` | `arn:aws:iam::<account>:user/<name>` |
| `arn:aws:iam::<account>:role/<name>` | `role` | `arn:aws:iam::<account>:role/<name>` |
| `arn:aws:sts::<account>:assumed-role/<name>/...` | `assumed-role` | `arn:aws:iam::<account>:role/<name>` |

When the app user is created, the script performs a trust policy merge — it retrieves the current assume-role policy document via `aws iam get-role`, locates the AWS principal statement, and appends the new user ARN to the existing array using `jq`. If no AWS principal statement exists, it injects a new statement. This idempotent merge ensures that re-running `setup-aws.sh` does not overwrite previously configured principals.

Sources: [setup-aws.sh](setup-aws.sh#L163-L218), [setup-aws.sh](setup-aws.sh#L394-L432)

## Role Permissions: Base Policy vs Session Policy

A common source of confusion in STS-based architectures is the relationship between the **role's attached permissions** and the **session policy** passed at AssumeRole time. The setup script attaches an inline policy named `IAMDynamicBasePermissions` to the role:

| Service | Actions | Scope |
|---------|---------|-------|
| S3 | `s3:*` | All resources |
| EC2 | `ec2:*` | All resources |
| Lambda | `lambda:*` | All resources |
| DynamoDB | `dynamodb:*` | All resources |
| RDS | `rds:*` | All resources |
| CloudWatch | `cloudwatch:*`, `logs:*` | All resources |
| Secrets Manager | `secretsmanager:*` | All resources |
| IAM | `iam:ListRoles`, `iam:GetRole` | All resources |

This base policy serves as the **permission ceiling**. When `STSService.assume_role_with_policy()` calls `boto3.client("sts").assume_role()` with the `Policy` parameter, AWS computes the session's effective permissions as the **intersection** of the role's identity-based policies and the session policy. This means:

- A session policy requesting `s3:GetObject` on a specific bucket will be **granted** (the role allows `s3:*`)
- A session policy requesting `iam:CreateUser` will be **denied** (the role only allows `iam:ListRoles` and `iam:GetRole`)
- A session policy requesting `s3:*` on all resources will be **granted** but the LLM is engineered to avoid generating wildcard policies for higher risk levels

The role is created with `--max-session-duration 43200` (12 hours), which sets the upper bound the role itself will accept. The effective session duration is further capped by the risk-based validation logic in `STSService.validate_duration()`.

## The STSService: Runtime Credential Issuance

### Initialization and Configuration Binding

The `STSService` is instantiated at application startup in `main.py` with the role ARN derived from the `AWSConfig` Pydantic model. The `AWSConfig` class constructs the role ARN dynamically from two environment variables:

| Environment Variable | Default | Purpose |
|---------------------|---------|---------|
| `AWS_ACCOUNT_ID` | *(required)* | 12-digit AWS account identifier |
| `AWS_ROLE_NAME` | `AgentPOCSessionRole` | Name of the IAM role to assume |

The `role_arn` property on `AWSConfig` composes these into the standard ARN format `arn:aws:iam::<account_id>:role/<role_name>`. This ARN is passed to the `STSService` constructor, which stores it and creates a `boto3.client("sts")` instance that inherits credentials from the environment (either `~/.aws/credentials` for local development or the `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` variables from `.env` in Docker deployments).

Sources: [config.py](backend/config.py#L27-L35), [main.py](backend/main.py#L36-L39), [docker-compose.yml](docker-compose.yml#L8-L9)

### The assume_role_with_policy Method

The core method `assume_role_with_policy()` accepts three parameters — the IAM policy document (as a Python dict), the session duration in fractional hours, and an optional session name. The method performs two layers of validation before issuing the STS call:

**Layer 1 — Absolute Bounds Enforcement** (hard limits): Duration is converted to seconds and checked against AWS STS constraints. The minimum is 900 seconds (15 minutes) and the maximum is 43200 seconds (12 hours). Violations raise `STSAssumeRoleError` immediately.

**Layer 2 — Risk-Based Capping** (policy limits): Before calling `assume_role_with_policy()`, the `issue_credentials` API endpoint uses `get_max_duration()` to determine the risk-appropriate ceiling. This is enforced upstream, but `STSService` also exposes `validate_duration()` for standalone validation.

The actual STS call passes the policy document as a JSON string via the `Policy` parameter. AWS validates the policy syntax server-side — if the policy is malformed, the STS API returns an error that surfaces as `STSAssumeRoleError`. On success, the response contains `Credentials` with `AccessKeyId`, `SecretAccessKey`, `SessionToken`, and `Expiration`. The method enriches this with `IssuedAt` (UTC now) and `SessionName` metadata before returning.

```

├──────────────────────────────────────────────────────────────────────┤

│         │                                                            │
│         ▼                                                            │
│  ┌───────────────────┐                                               │
│  │ Convert hours →   │    duration_seconds = int(hours * 3600)       │
│  │ seconds           │                                               │
│  └────────┬──────────┘                                               │
│           │                                                          │
│           ▼                                                          │
│  ┌───────────────────┐    duration_seconds < 900?  ──▶ ValueError   │
│  │ Validate bounds   │    duration_seconds > 43200? ──▶ ValueError   │
│  └────────┬──────────┘                                               │

│  ┌───────────────────────────────────────────────┐                   │
│  │ boto3 STS client.assume_role(                 │                   │
```

### Risk-Based Duration Enforcement

The risk-to-duration mapping encodes a core security posture: higher-risk requests receive shorter-lived credentials, minimizing the blast window if credentials are leaked or misused. Both the API endpoint and the `STSService` enforce this:

| Risk Level | Max Duration | Typical Use Case |
|-----------|-------------|-----------------|
| `low` | 12 hours | Read-only access, single-service queries |
| `medium` | 4 hours | Multi-service read, limited write operations |
| `high` | 2 hours | Destructive actions, broad permissions |
| `critical` | 1 hour | `*:*` on `*`, security-sensitive operations |

In the API flow, `get_max_duration()` caps the requested duration before it reaches `STSService`, and `STSService.validate_duration()` provides an independent check. The `min(requested, max_allowed)` computation ensures that a user requesting 12 hours for a `critical`-risk policy receives only 1 hour — with a logged warning.

### Idempotent Trust Policy Updates

When the target role already exists, the script prompts the user and offers to update the trust relationship. The trust policy merge logic (lines 403–426 of `setup-aws.sh`) uses `jq` to locate the existing AWS principal statement and append the new ARN to the array, deduplicating with `unique`. If no AWS principal statement exists, it injects a fresh statement. This design ensures that re-running the script to add new principals never removes existing ones.

The `role_arn` property on `AWSConfig` composes the full ARN string using an f-string pattern: `arn:aws:iam::{account_id}:role/{role_name}`. This avoids storing the full ARN as a separate variable and ensures that changing either component automatically updates the ARN used by `STSService`. ## Error Handling and Diagnostics

When `sts:AssumeRole` fails, the `STSService` catches the boto3 exception and wraps it in `STSAssumeRoleError` — a custom exception hierarchy rooted at `STSServiceError`. The API endpoint in `main.py` catches this and returns a structured HTTP 503 response with actionable diagnostics:

```python
except STSAssumeRoleError as e:
    raise HTTPException(
        status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
        detail=f"🔑 **AWS Credential Issue**\n\n"
               f"Unable to issue temporary credentials. This could be due to:\n"
               f"• **Invalid AWS credentials** ...\n"
               f"• **Role doesn't exist** ...\n"
               f"• **Permission denied** ...\n"
    )
```

The three most common failure modes and their root causes:

| Symptom | Likely Cause | Resolution |
|---------|-------------|------------|
| `AccessDenied` from STS | Caller's ARN not in role's trust policy | Re-run `setup-aws.sh` or manually add the principal to the trust policy |
| `ValidationError` on Policy parameter | Malformed session policy JSON | Check the LLM prompt output — the policy may have invalid syntax |
| `Region not found` / credential timeout | Missing `AWS_DEFAULT_REGION` or invalid access keys | Verify `.env` values and run `aws sts get-caller-identity` |

The error detail includes the computed role ARN from the configuration, making it easy to verify that the application is targeting the correct role.

## Manual Setup Alternative

If the automated script is not suitable (e.g., in organizations with infrastructure-as-code requirements), the equivalent AWS CLI commands to create the role manually are:

**Step 1 — Create the trust policy document** (`trust-policy.json`):
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "sts.amazonaws.com" },
      "Action": "sts:AssumeRole"
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/iam-dynamic-app"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Step 2 — Create the role** with a 12-hour maximum session duration:
```bash
aws iam create-role \
  --role-name AgentPOCSessionRole \
  --assume-role-policy-document file://trust-policy.json \
  --description "IAM-Dynamic JIT access role" \
  --max-session-duration 43200
```

**Step 3 — Attach the base permissions policy**:
```bash
aws iam put-role-policy \
  --role-name AgentPOCSessionRole \
  --policy-name IAMDynamicBasePermissions \
  --policy-document file://base-policy.json
```

**Step 4 — Configure environment variables** in `.env`:
```bash
AWS_ACCOUNT_ID=123456789012
AWS_ROLE_NAME=AgentPOCSessionRole
```

**Step 5 — Verify** the trust relationship:
```bash
aws iam get-role --role-name AgentPOCSessionRole \
  --query 'Role.AssumeRolePolicyDocument' --output json
```

## Security Considerations

The architecture implements several defense-in-depth layers around the STS credential issuance path. Understanding these is essential for production deployments.

**Trust Policy Scoping**: The trust policy should contain *only* the IAM principals that need to call AssumeRole through the application. Adding broad principals (e.g., the entire AWS account) defeats the purpose of the trust boundary. The setup script's automatic detection ensures only the calling identity and the dedicated `iam-dynamic-app` user are added.

**Session Policy Enforcement**: The LLM-generated session policy is the primary security boundary. Even if the role's base policy grants `s3:*`, a session policy specifying only `s3:GetObject` on a single bucket means the resulting credentials cannot perform any other S3 operation. This is enforced by AWS at the policy evaluation layer — there is no way for the application to bypass it.

**Duration as Risk Proxy**: Shorter durations are a direct mitigation for credential exfiltration. A 1-hour `critical`-risk credential that leaks is dangerous for a bounded window, after which it is permanently invalid. Combined with CloudTrail logging of all AssumeRole calls, this provides both prevention and detection capabilities.

**Credential Isolation via Dedicated IAM User**: The `--skip-user` flag exists for convenience, but production deployments should create a dedicated `iam-dynamic-app` IAM user. This isolates the application's AWS identity from any individual developer's credentials, enabling independent key rotation and audit trail separation.
